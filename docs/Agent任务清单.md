## P0 环境准备

### T0 环境准备与工具链验证
- **目标**：确认本机具备可编译、可测试、可调试、可版本管理的完整 C++ 开发环境。
- **输入**：本仓库（`student-mis/`）、本机已安装的 Git / GCC / CMake / Ninja。
- **关键步骤**：
  1. 执行 `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug` 生成构建系统；
  2. 执行 `cmake --build build` 编译全部目标，确认零警告；
  3. 执行 `./build/mis_tests.exe`，确认环境自检用例全绿（30 个用例、0 失败）；
  4. 执行 `./build/student_mis.exe --selfcheck` 打印编译器与语言标准；
  5. 执行 `./build/student_mis.exe` 走一遍菜单，确认交互可用。
- **预期产出**：构建成功截图；`mis_tests.exe` 全绿输出；`--selfcheck` 环境信息截图；
  确认 `__cplusplus == 201703`（C++17 已启用）。
- **人工把关点**：环境不通则一切后续任务无意义，此任务验收未通过前不得进入 T1。

## P1 需求分析与设计

### T1 需求分析与边界条件枚举
- **目标**：把自然语言需求转成可测试的功能清单与边界条件清单。
- **输入**：任务书"实验内容"六项功能需求；`include/student.h` 中已有的字段定义。
- **关键步骤**：
  1. 向 AI 提问：`请从"输入—处理—输出—异常"四个角度分析本需求，列出所有异常场景`；
  2. 逐条人工核对，补上 AI 容易漏掉的场景（空表、单节点、重复主键、成绩越界、学号为 0/负数）；
  3. 把每个功能拆成"正常路径 / 边界路径 / 异常路径"三类用例；
  4. 输出边界条件清单表。
- **预期产出**：功能需求清单（初始化、插入、查询、删除、遍历、统计）；
  边界条件清单（≥ 10 条，含空表、唯一节点、重复学号、删除首/尾/根节点等）。
- **人工把关点**：AI 常把"重复学号"和"学号非法"混为一类，必须人工区分——
  前者是业务规则冲突，后者是输入数据非法。

### T2 成绩数据类型选型论证
- **目标**：为"保留一位小数的成绩"选定数据类型，并给出可验证的理由。
- **输入**：`Student::score` 字段现状；任务书步骤 5 明确要求讨论此问题。
- **关键步骤**：
  1. 与 AI 讨论候选方案：`int`（分为单位）、`float`、`double`、`std::string`（定点串）；
  2. 逐项列出精度、取值范围、比较/统计代价、序列化代价；
  3. 用一段小程序实测 `float` 累加 100 万次与 `double` 的误差差异；
  4. 给出结论并写入报告"结果分析"。
- **预期产出**：选型对比表 + 结论（本工程采用 `double`，并说明整数"分×10"方案作为替代思路的取舍）。
- **人工把关点**：AI 往往直接答 `double` 而不给理由；必须要求它给出**可测量的对比实验**。

### T3 模块拆分与接口（契约）设计
- **目标**：把系统拆成可独立开发、可替换的子模块，先定接口后写实现。
- **输入**：T1 的功能清单；`include/student_db.h` 抽象接口草案。
- **关键步骤**：
  1. 与 AI 讨论拆分粒度：`Student` 记录模块、`StudentDB` 抽象接口、单链表实现、BST 实现、
     校验规则、主程序菜单、测试框架；
  2. 明确每套方法的**返回值语义**与 **out 参数语义**（例如 `find` 未命中时是否修改 `out`）；
  3. 确认两套实现必须满足同一契约，从而让同一份测试与同一份菜单代码复用；
  4. 形成模块清单表（模块名 / 职责 / 依赖 / 对外的接口）。
- **预期产出**：模块拆分清单表 + 接口契约说明（含 6 个功能方法各自的返回语义）。
- **人工把关点**：拆分粒度过粗会让 AI 一次生成过多代码而无法评审；过细则产生大量胶水代码。
  判断标准：**每个模块应能独立写完并独立测试**。

## P3 单链表模块开发

> 通用要求：每个模块都遵循同一节奏 —— **写提示词 → AI 生成 → 人工 CR → 补单元测试 → 测试全绿 → Git 提交**。

### T5 模块 A-1：`SllStudentDB::insert`
- **目标**：实现带头结点单链表的按学号升序插入，并拒绝重复学号与非法数据。
- **输入**：`include/sll_student_db.h`（节点结构、`head_`、`count_`）、
  `include/student.h` 的 `validate()`、`src/sll_student_db.cpp` 的 `TODO(模块 A-1)`。
- **关键步骤**：
  1. 下发限定范围提示词（只实现 `insert`，不动头文件）；
  2. 让 AI 先列边界：空表、插表头之后、插表尾、重复学号、非法数据；
  3. 人工评审：是否先校验后插入、重复检查是否覆盖、`count_` 是否只在成功分支递增；
  4. 补入 `tests/test_sll.cpp` 中对应断言并跑测试。
- **预期产出**：`insert` 实现 + 至少 5 组通过的单链表插入用例。
- **人工把关点**：**重复主键校验**。AI 常见缺陷是直接用尾插法追加，
  完全不做"先查再插"，导致同一学号出现两条记录。

### T6 模块 A-2：`SllStudentDB::remove`
- **目标**：实现单链表按学号删除。
- **输入**：已完成 `insert` 的链表；`TODO(模块 A-2)`。
- **关键步骤**：
  1. 下发提示词，要求用"前驱指针 + 当前指针"双指针方式；
  2. 评审三种删除位置：第一个数据节点（前驱是头结点）、中间节点、尾节点；
  3. 评审唯一节点被删除后 `head_->next` 是否为 `nullptr`；
  4. 补用例：删除首个 / 尾部 / 唯一 / 不存在 共 4 组。
- **预期产出**：`remove` 实现 + 4 组通过用例。
- **人工把关点**：删除后必须**立即** `delete` 并更新 `count_`；
  AI 常见缺陷是删除后仍沿用旧指针（use-after-free）或漏减计数。

### T7 模块 A-3 / A-4：`find` / `traverse`
- **目标**：实现有序链表的查找（含提前终止剪枝）与升序遍历输出。
- **输入**：已完成增删的链表；`TODO(模块 A-3)`、`TODO(模块 A-4)`。
- **关键步骤**：
  1. 提示词中明确"链表已按 id 升序，命中 id 小于当前节点时可提前结束循环"；
  2. 评审 `traverse` 是否先 `out.clear()`、是否按升序 push；
  3. 用例：命中、未命中、空表遍历、乱序插入后仍升序。
- **预期产出**：`find` / `traverse` 实现 + 4 组通过用例。
- **人工把关点**：AI 容易写成"整表扫描"，丢掉有序性带来的剪枝——
  这会直接影响后续与 BST 的性能对比结论。

### T8 代码评审 CR（单链表整体）
- **目标**：对单链表模块做一次完整的人工评审并留下记录。
- **输入**：`src/sll_student_db.cpp` 全量代码 + `AGENTS.md` 的 CR 检查清单。
- **关键步骤**：逐条核对 CR 清单的 9 项检查点；对每条问题记录"现象 / 位置 / 修改方案"；
  对认定的缺陷要求 AI 给出修复补丁（一次只修一个）。
- **预期产出**：CR 记录表（问题清单 + 修复前后对比），作为报告"迭代开发记录"条目。
- **人工把关点**：CR 的结论由人负责——AI 自评"代码没问题"不具备效力。

### T9 单元测试（单链表）
- **目标**：把 `tests/test_sll.cpp` 中全部 `MIS_PENDING` 转为真实断言并跑绿。
- **输入**：已完成的单链表实现；`tests/test_framework.h` 的断言宏。
- **关键步骤**：按文件内注释启用断言 → `cmake --build build` → `./build/mis_tests.exe`
  → 修正失败项 → 直到全部通过。
- **预期产出**：单链表 11 组用例全部通过。
- **人工把关点**：**测试通过不等于正确**——要主动质疑断言是否覆盖了边界，
  可以让 AI 反问你："哪些分支还没被测到？"

## P4 BST 模块开发

### T10 模块 B-1 / B-3：`insert` / `find`
- **目标**：以学号为关键字建立 BST，实现插入与 O(树高) 查找。
- **输入**：`include/bst_student_db.h`（`root_`、`count_`）、`TODO(模块 B-1)`、`TODO(模块 B-3)`。
- **关键步骤**：
  1. 提示词明确"不允许重复键""空树时新节点即根"；
  2. 评审比较方向（左小右大是否写反）、`count_` 递增位置；
  3. 用例：乱序插入后中序升序、命中、未命中、空树。
- **预期产出**：`insert` / `find` 实现 + 4 组通过用例。
- **人工把关点**：**比较方向写反**与**重复键未拦截**是 AI 的高频缺陷，必须逐行核对。

### T11 模块 B-2：`remove`（本实验最难点）
- **目标**：实现 BST 删除的三种情形，保证树结构与计数同时正确。
- **输入**：已建好的 BST；`TODO(模块 B-2)`。
- **关键步骤**：
  1. 先让 AI **只输出**"三种情形分别如何处理"的文字方案，人确认后再要代码；
  2. 情形 (a) 叶子：直接删；(b) 单孩子：孩子顶替；
     (c) 双孩子：取**中序后继**（右子树最小值）替换数据，再删除后继原位置；
  3. 逐行核对情形 (c) 的指针接续——这是 AI 最容易漏释放或断链的地方；
  4. 用例：删叶子、删单孩子（左/右各一）、删双孩子、删根节点、删不存在。
- **预期产出**：`remove` 实现 + 6 组通过用例 + CR 记录。
- **人工把关点**：情形 (c) 必须**人工逐行**确认；建议同时检查是否发生内存泄漏
  （可用 GDB 或 Valgrind/Dr.Memory 辅助）。

### T12 模块 B-4：`traverse` + CR + 单元测试
- **目标**：中序遍历实现升序输出，并补齐 BST 的整体 CR 与测试。
- **输入**：`TODO(模块 B-4)`；`tests/test_bst.cpp` 全部待启用用例。
- **关键步骤**：
  1. 实现中序遍历（递归或显式栈），空树必须安全；
  2. 跑 `tests/test_bst.cpp` 的 12 组用例并修正；
  3. 做一次 BST 整体 CR（重点：`clear()` 的释放路径、退化风险）。
- **预期产出**：BST 12 组用例全部通过 + BST 的 CR 记录。
- **人工把关点**：`clear()` 已给出实现，但仍需人工确认它不会重复释放 / 漏释放。

## P5 验证与对比

### T13 回归测试与缺陷迭代修复
- **目标**：在两种实现同时存在的情况下，确保互相不干扰、全量测试始终全绿。
- **输入**：全部模块 + 完整测试套件。
- **关键步骤**：
  1. 跑全量测试 `ctest --output-on-failure`；
  2. 对每个失败项定位是"实现缺陷"还是"测试写错"，**分别**处理；
  3. 每修一处即重跑全量测试，确认无回归；
  4. 用 `gdb` 或加入 `-fsanitize=address` 复跑一次，排查内存问题；
  5. 记录缺陷台账（编号 / 现象 / 根因 / 修复方式 / 是否回归）。
- **预期产出**：缺陷台账 + 全量测试全绿的最终输出截图。
- **人工把关点**：区分"改代码"还是"改测试"是**人的判断**——
  绝不能让 AI 通过放宽断言来"修好"测试。

### T14 单链表 vs BST 性能对比实验
- **目标**：用数据回答"两种实现各自适合什么业务场景"。
- **输入**：`tools/benchmark.cpp`；两种实现的完整代码。
- **关键步骤**：
  1. `./build/mis_benchmark.exe 5000 2000` 得到基础数据；
  2. 改写插入顺序为**严格递增**（1,2,3,…），观察 BST 退化为链表的性能崩塌；
  3. 记录三组数据：建表耗时、命中查询总耗时 / 单次均值、未命中查询总耗时；
  4. 结合复杂度分析（SLL 查找 O(n)；BST 随机 O(log n)、最坏 O(n)）解释现象。
- **预期产出**：性能对比数据表（≥ 2 组规模 × 2 种实现）+ 数据解读结论。
- **人工把关点**：对比必须在**同机、同构建类型、同数据规模**下进行；
  测得的单次微秒级数据要警惕噪声，必要时加大规模取平均。

## P6 交付

### T15 Git 提交与版本变更记录
- **目标**：让每一次代码演进在版本历史中可追溯，形成"迭代开发记录"的客观证据。
- **输入**：已通过 CR 与测试的模块代码；`AGENTS.md` 的提交纪律。
- **关键步骤**：
  1. 每个模块通过 CR + 测试全绿后提交一次，禁止攒成一次大提交；
  2. 提交信息按 `<模块> <动作>: <一句话说明>` 编写；
  3. 确认 `build/`、`*.exe`、IDE 配置未被提交（已在 `.gitignore` 中排除）；
  4. 用 `git log --oneline` 导出提交历史，作为报告的"迭代开发记录"。
- **预期产出**：≥ 8 次语义化提交；`git log --oneline` 输出截图。
- **人工把关点**：提交粒度是否真的对应"一次评审"——按需用 `git rebase -i` 整理历史。

### T16 实验报告与思考题产出
- **目标**：按任务书要求组织出可提交的实验报告。
- **输入**：本清单全部任务的产出物；`docs/实验报告模板.docx`。
- **关键步骤**：
  1. 按模板逐节填写：目的 → 需求分析 → 模块拆分 → 迭代记录 → 源码 → 测试 → 总结；
  2. 附上关键运行截图（编译零警告、测试全绿、性能对比表、程序交互）；
  3. 完成三道思考题（一次性投喂 vs 拆分开发；AI 高频出错点与人工把关；单链表与 BST 的适用场景）；
  4. 附 Git 提交历史与 Agent 协作记录。
- **预期产出**：完整的实验报告（含源代码清单、测试用例、运行截图、思考题回答）。
- **人工把关点**：思考题必须结合**自己本次的真实经历**作答，
  用 T2、T4、T8、T13 记录中的具体例子支撑，不接受泛泛而谈。
